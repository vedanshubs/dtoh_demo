# UBS eScreen POC 2 — Data Visualization Mock Data Design
*2026-05-11*

## Overview

Mock data strategy for POC 2 (Conversational Data Visualization). A Client Admin queries drug test data in plain English through a chat interface and receives answers as numbers, tables, or charts. All data is scoped to UBS's client account, enforced at the MCP server level.

The mock uses the real DTOH table structure (column names match the production schema exactly) in the same MySQL Docker instance as POC 1. Queries written against mock data are representative of what production queries would look like — no throwaway SQL.

---

## Local Database Setup

Same MySQL Docker container as POC 1:

```bash
docker run -d \
  --name escreen-db \
  -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=root \
  -e MYSQL_DATABASE=escreen \
  -e MYSQL_USER=escreen \
  -e MYSQL_PASSWORD=escreen \
  mysql:8
```

**To browse data visually:** Use MySQL Workbench, TablePlus, or DBeaver — connect to `localhost:3306`, user `escreen`, password `escreen`.

## Schema Mapping — DTOH → MySQL

The real schema is SQL Server (`DTOH` schema, `DrugTesting` database). For the POC we replicate the relevant tables in MySQL, keeping column names identical and adjusting only syntax (`IDENTITY` → `AUTO_INCREMENT`, `datetime2` → `DATETIME`, `nvarchar` → `VARCHAR`).

### Real DTOH hierarchy

```
CollectionOrder          ← one per test order placed
    └── TestReport       ← central record per ordered service
        └── DrugReport   ← result details + all 5 date milestones
            └── PanelResult        ← one per test panel
                └── SubstanceResult  ← one per analyte tested
```

### What each MCP tool queries

| Tool | Tables joined | Core filter |
|---|---|---|
| `get_results_summary` | `CollectionOrder` → `TestReport` → `DrugReport` | `AccountNumber = UBS001`, date range on `DateOfService` |
| `get_pipeline_status` | `CollectionOrder` → `TestReport` → `StatusType` | `AccountNumber = UBS001`, `ResultTypeId IS NULL` (not yet finalized) |
| `get_analyte_breakdown` | `CollectionOrder` → `TestReport` → `DrugReport` → `PanelResult` → `SubstanceResult` | `AccountNumber = UBS001`, date range |
| `get_turnaround_stats` | `CollectionOrder` → `TestReport` → `DrugReport` | `AccountNumber = UBS001`, `VerificationDate IS NOT NULL` |

### Data tables (generated by script)

#### `CollectionOrder`
One row per test. The account scoping anchor.

Key columns used:
- `CollectionOrderId` INT AUTO_INCREMENT PK
- `AccountNumber` VARCHAR(6) — always `'UBS001'` for this client
- `TestReason` VARCHAR(50) — matches `TestReason.TestReasonTitle`
- `IsDOT` TINYINT(1)
- `CostCenter` VARCHAR(50) — UBS office: `NY-HQ`, `NJ-Weehawken`, `CT-Stamford`, `IL-Chicago`
- `RecordCreatedDate` DATETIME

#### `TestReport`
One row per ordered service, linked to `CollectionOrder`.

Key columns used:
- `TestReportId` INT AUTO_INCREMENT PK
- `CollectionOrderId` INT FK
- `StatusId` INT FK → `StatusType` (NULL = pipeline, 7 = completed)
- `ResultTypeId` INT FK → `ResultType` (NULL while in-progress)
- `IndustryTypeId` INT FK → `IndustryType`
- `DateOfService` DATETIME — the collection date
- `ReasonForTest` VARCHAR(100)
- `Regulation` VARCHAR(20) — `'DOT'` or `'Non-DOT'`
- `eScreenStatusCode` VARCHAR(50)
- `eScreenStatusDescription` VARCHAR(255)
- `TestReportAccountNumber` VARCHAR(100) — `'UBS001'`
- `CreatedOn` DATETIME

#### `DrugReport`
One row per finalized TestReport. NULL = test still in pipeline.

Key columns used:
- `DrugReportId` INT AUTO_INCREMENT PK
- `TestReportId` INT FK
- `Disposition` VARCHAR(10) — `'Negative'`, `'Positive'`, etc.
- `SampleType` VARCHAR(20) — `'Urine'`, `'Hair'`, `'Oral Fluid'`, `'Breath'`
- `SpecimenType` VARCHAR(100) — same as SampleType (redundant field, matches real schema)
- `CollectionDateTime` DATETIME — milestone 1
- `LabReceivedDate` DATETIME — milestone 2
- `LabReportDateTime` DATETIME — milestone 3
- `MROReceivedDate` DATETIME — milestone 4
- `VerificationDate` DATETIME — milestone 5
- `LabName` VARCHAR(100) — `'Quest Diagnostics'` or `'LabCorp'`
- `CreatedOn` DATETIME

#### `PanelResult`
One row per DrugReport (one panel per test for POC simplicity).

Key columns used:
- `PanelResultId` INT AUTO_INCREMENT PK
- `DrugReportId` INT FK
- `ResultTypeId` INT FK
- `PanelName` VARCHAR(255) — e.g. `'5-Panel Urine'`

#### `SubstanceResult`
One row per analyte per test. Generated for all finalized tests — negative analytes included (needed for correct denominators in breakdown queries).

Key columns used:
- `SubstanceResultId` INT AUTO_INCREMENT PK
- `PanelResultId` INT FK
- `SubstanceId` INT FK
- `AnalyteName` VARCHAR(100) — matches `Substance.DisplayName`
- `Disposition` VARCHAR(5) — `'Pos'` or `'Neg'`
- `SpecimenType` VARCHAR(20)
- `SampleTypeId` INT FK

## The Story Arc — Deliberate Patterns for Demo

The data has baked-in narratives that Claude should surface when the admin asks the right questions.

### Story 1: THC spike at NY-HQ in Q4 2025

| Period | NY-HQ positive rate | Other offices |
|---|---|---|
| Q3 2025 (Jul–Sep) | ~3% | ~3% |
| Q4 2025 (Oct–Dec) | **~9%** | ~3% |
| Q1 2026 (Jan–Mar) | ~5% | ~3% |
| Q2 2026 (Apr–May) | ~3.5% | ~3% |

Spike is driven almost entirely by THC positives at NY-HQ. The pattern allows progressive drill-down:
- *"Any trends I should know about?"* → spike surfaces
- *"Which substance?"* → THC
- *"Which office?"* → NY-HQ
- *"Is it improving?"* → Yes, Q1 2026 already trending down

### Story 2: For Cause surge in Q1 2026

Normal For Cause volume: 5–7/quarter. Q1 2026: **18 For Cause tests** (~3× baseline). This is the HR response to the Q4 2025 spike — the timeline is coherent: spike → investigation → resolution.

### Story 3: Hair tests have disproportionately high positive rate

Overall positive rate: ~4.5%. Hair follicle positive rate: **~9%** (longer detection window). Creates a meaningful answer to *"does specimen type affect outcomes?"*

### Story 4: IL-Chicago misses SLA most often

| Office | Avg end-to-end | SLA compliance |
|---|---|---|
| CT-Stamford | 3.8 days | ~95% |
| NY-HQ | 4.2 days | ~90% |
| NJ-Weehawken | 4.5 days | ~88% |
| IL-Chicago | **5.6 days** | **~65%** |

IL-Chicago misses the 5-day SLA on roughly 1 in 3 tests. Interesting answer to *"are we hitting our SLA everywhere?"*

### Full demo conversation arc

> **Admin:** *"Give me a summary of drug test results this year"*
> → Overall totals, positive rate, breakdown by reason
>
> **Admin:** *"Anything unusual compared to last quarter?"*
> → THC spike at NY-HQ in Q4 2025 surfaced
>
> **Admin:** *"Which substance is driving it?"*
> → THC breakdown by quarter, NY-HQ isolated
>
> **Admin:** *"Break it down by office — which location has the highest positive rate?"*
> → CostCenter breakdown, NY-HQ flagged
>
> **Admin:** *"What about our turnaround times — are we hitting SLA?"*
> → Overall 87%, IL-Chicago specifically flagged at 65%
>
> **Admin:** *"How many tests are still in progress right now?"*
> → Pipeline view, 4–5 overdue flagged

## What Is Explicitly Out of Scope

- No `AlcoholReport`, `OccHealthReport`, or occupational health data — drug tests only
- No billing, audit logs, notifications, permissions, or WorkQueue tables
- No multi-client data — single UBS account (`UBS001`) only
- No real authentication — `client_id` hardcoded as `'UBS001'` in `.env`
- Happy path queries only — no error handling for malformed SQL or missing data
- `get_analyte_breakdown` and `get_turnaround_stats` built after `get_results_summary` + `get_pipeline_status` are validated
